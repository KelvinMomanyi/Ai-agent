## Confirmed backend defect

The order webhook passes `extractOrderAttribution(...).lineItems` to [`incrementOrderAffinities`](../app/models/product.server.ts). Those runtime objects contain `quantity`, `price`, `totalDiscount` and sometimes `offerId` in addition to `productId` and `variantId`.

The function keeps the whole runtime object when deduplicating variants, then spreads it into `productVariantOrderStat.createMany()` and also uses it in `updateMany({where: {shop, OR: variants}})`. [`ProductVariantOrderStat`](../prisma/schema.prisma) has only its identity fields, product relation and order count; these extra order-line fields are invalid input.

Production logs for our exact QA product/variant/offer IDs show:

```text
AOVBoost webhook failed:
Invalid prisma.productVariantOrderStat.createMany() invocation
data includes quantity, price, totalDiscount, offerId
```

The transaction fails before [`api.webhooks.tsx`](../app/routes/api.webhooks.tsx) reaches `markOfferConversion`. Repeated deliveries reproduce the same failure. This is the direct evidenced attribution blocker, **separate from Redis DNS failures**.

The proposed narrow correction is to project each variant to `{productId, variantId}` before deduplication/writing and before building the `OR` filters. The existing performance integration test calls `incrementOrderAffinities` without line items, leaving this variant branch unexercised. A regression should pass full extracted attribution lines, including their extra fields, through the real function and verify schema-compatible write/filter inputs, atomicity and duplicate-delivery behavior. No schema migration is indicated by this input-shape defect.

**Not applied:** the original implementation scope excluded backend changes. An explicit scope question to fix this backend model and prepare a reviewed release is pending. No backend code or deployment was changed during verification.
