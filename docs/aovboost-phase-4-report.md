# aovboost Phase 4 report

13 November 2026. Phase 4 implements the shared storefront identity, gesture-driven chat doorway, product/cart handoff and mobile exit signals. `agent_core_enabled` remains **off by default**. Phases 5–6 are not implemented. Nothing was deployed; all verification described here uses local tests and synthetic Shopify/app-proxy responses.

## Result

With the flag enabled and the assistant reachable, browsing starts with a quiet launcher. An offer response cannot open the conversation. A trusted launcher click, keyboard action or existing chat CTA opens the same conversation; scripted open events without a shopper gesture are ignored. Toast and exit CTAs supply a handoff object and the doorway rebuilds its facts from current AgentContext rather than trusting externally supplied copy.

`AgentVoice` supplies one shop-derived assistant name, a letter avatar, greeting, product-specific nudge/opening templates, quick replies and new error/action copy. The launcher, toast, exit offer and chat header use that identity. Existing provider surfaces receive the same identity through the flagged renderer hook. Existing merchant payload text on other surfaces remains in place for Phase 5's guard/template work.

The handoff includes the trigger, verified product ID, the selected variant from an unambiguous purchase form when available, an anonymous cart snapshot and a relevant opening line. Existing product-view metadata supplies titles; the Phase 3 shared PDP read can also populate missing metadata without another request. The chat sends product ID through the existing recognized `storefrontContext.productId`; selected variant ID is additive frontend metadata. **The current backend does not interpret that selected-variant field**, so transporting it is not model-level selected-variant verification. The existing live `cartContext` read remains authoritative for server cart actions. Opening chat does not automatically send a shopper message or start an AI request.

The new conversation presentation loads on first intent and reuses the existing signed POST, SSE streaming, product cards, variant controls, cart actions and cart refresh implementation. It adds a responsive dialog, keyboard trap, Escape/backdrop close, focus return, accessible typing status, quick replies and an explicit retry state. A failed reply keeps the open conversation available even when health becomes unhealthy. Retrying probes health and requires a shopper action. A reply interrupted after a cart action does not offer automatic message replay, avoiding a duplicate write. If the lazy module itself fails to load, an honest **Reload page** action resets the browser's failed-module cache; chat still requires another gesture after reload.

Chat cart actions retain `aov_chat`. Undo is offered only after a confirmed, isolated line change with readable before/after snapshots. Before undo, both the current cart fingerprint and mutation revision must still match. It restores the prior quantity or exact removed line (including properties/selling plan), refuses intervening edits and verifies the resulting cart. Properties remain in memory, never storage/logs. Undo calls the same locale-aware mutation/section-refresh helper; its additive `undo: true` event metadata prevents a restoration add from becoming a new standardized `accepted` event. It cannot trigger cart upsell. Opening chat can close an active native cart drawer through its public `close()` method to avoid competing focus traps. After a cart action, that method is used only if the refresh opened a previously closed drawer; the existing refresh path is preserved.

Toast remains **desktop-only**. It has a keyboard-reachable dismiss button and a nine-second countdown paused while hovered **or** focused. Mobile gets the quiet launcher and an exit bottom sheet. Mobile exit observes cumulative fast scroll-up, 25-second idle and nonblocking same-document back navigation in engaged sessions. It never inserts history entries, cancels navigation or traps the browser Back action. Full document back navigation may leave before an offer can appear. Existing Arbiter frequency caps, once-per-session exit, dismissal backoff, chat/checkout suppression and one-foreground rule still apply.

## Session continuity and privacy

The flagged UI keeps up to 20 replay messages in core-owned memory across closing/reopening the conversation and same-document navigation. It does **not** read or write the legacy browser transcript cache. The existing backend already loads session conversation context for subsequent replies, so normal signed-session continuity across a document reload remains available to the model.

**Visible transcript replay after a full document reload is not implemented.** The existing GET chat endpoint is only a reachability probe, not a history reader. Adding a transcript endpoint would cross the backend boundary, and persisting raw shopper messages in browser storage would violate the prompt's privacy constraint. With blocked storage, the current page continues working; cross-document continuity also depends on the existing session authentication/storage behavior. Legacy flag-off storage behavior is preserved.

## Enable and debug

Set the existing flag before SDK initialization, then reload:

```js
window.AOVBoost = { ...window.AOVBoost, agent_core_enabled: true };
```

The existing settings-provided flag is also supported. Default is off; no merchant setting UI or flagging dependency was added. Use `?aov_debug=1` and `window.__AOVBOOST_DEBUG__.decisions()` for the existing last-50 decision buffer. With debug off, the new modules write no console output. Ordinary browser network diagnostics for a deliberately failed HTTP request are not application debug logs.

Existing event names are retained, including `aovboost:open-chat`, `chat_opened`, `chat_closed`, `widget_click`, `widget_dismiss` and the public legacy `exit_intent` trigger. Mobile reuses that backend trigger and publishes the already-defined internal `exit_intent_mobile` signal. The only cart event addition is optional `undo: true`; selected variant metadata is additive on the chat request. No compatibility rename/shim is needed. Existing chat-opening CTAs work synchronously inside a trusted click/key gesture and receive freshly built context.

The new conversation chunk is requested only on first shopper intent; browser tests verify that boundary. The legacy chat implementation remains in the initial SDK so flag-off delivery/behavior does not gain another request. This phase lazy-loads the new managed presentation, not all historical chat code. The theme runtime remains conditionally loaded by the existing adaptive-cart path.

The initial ceiling stays **170,000 raw bytes**. The combined ceiling is explicitly increased from **255,000 raw / 73,000 gzip** to **275,000 raw / 82,000 gzip** for the new managed UI, identity and mobile observers, counting shared and lazy artifacts. Total growth is **15,271 raw / 8,093 gzip**; theme minification offsets part of that addition. Standalone CSS remains 27 raw / 47 gzip bytes. No dependency was added.

## Open issues, ranked

1. **AI health remains transport-level until a real reply.** GET `/chat` does not exercise billing, Redis or the model. Actual failures feed the breaker and keep retry UI honest, but backend reliability is unchanged and not live verified.
2. **No full-reload transcript replay.** Normal server conversation context exists, while visible replay is memory-only to avoid storing PII. A future history API requires separate backend scope/review; do not solve it by persisting raw shopper text.
   The handoff also transports selected variant ID, but existing server context/prompt builders consume product-level page fields only. Model-level use of selected variant needs separately authorized backend work; no such prompt change was made here.
3. **Real theme/device integration is unverified.** Physical touch keyboards, Safari, merchant CSS, native focus traps and full document Back behavior need live QA. Mobile Back is deliberately nonblocking. Toast remains desktop-only.
4. **Phase 5 truthfulness work is still required.** Real reward-linked discount progress, finalized countdown/social-proof/inline payload guards and remaining safe templates are not completed here. The discount bar still does not itself create/apply discounts. The storefront post-purchase action still adds to a cart, not a completed order; the checkout extension was not changed.
5. **Offers still need backend authorization.** AI-independent catalog fallback stays within an approved offer; a complete app-proxy/plan outage hides the surface instead of bypassing merchant/plan gates. Billing/Redis remediation stays out of scope.
6. **Analytics need Phase 6 QA.** Standardized acceptance excludes undo restoration; legacy raw cart events retain compatibility and additive undo metadata. Backend reporting has not been changed to interpret that metadata or validated against completed orders. Holdout assignment/dashboard work remains deferred.
7. **Performance is measured locally only.** The initial SDK still contains legacy chat code. Combined size has an explicit larger budget; real storefront CLS, request timing and loaded-byte measurements are required before enabling this for shoppers.

## Recommended Phase 5 starting point

Start with a read-only inventory of real reward/campaign/verified-proof/alert payloads and their existing schemas. Then implement reward-linked discount progress, strict future-end countdown expiry, verified social-proof minimum/window labels and payload-ID alert dismissal through the existing adapters. Keep the flag off by default, retain the cart-refresh/source tests and keep backend discount creation and checkout-extension behavior outside that frontend phase unless separately authorized.
